# Заводской генератор партии аппаратов

Скрипт `tool/provision_devices.py` работает локально, без обращения к облаку и без
ключей Supabase (публичный ключ — только как значение для записи в аппарат).

## Как пользоваться

```
export PROVISION_ANON_KEY='<публичный ключ sb_publishable_…>'
tool/provision_devices.py --org-id <uuid организации-изготовителя> \
    --prefix CARFOG- --start 100 --count 20 --cloud-url https://<проект>.supabase.co
# или список:  --list ids.txt   (по одному номеру в строке, # — комментарий)
# кольцо раскатки (по умолчанию test):  --ring test | early | all
```

**Кольцо.** Генератор записывает `devices.ring` явно в каждом `insert` (по умолчанию
`test`). Иначе новые аппараты получили бы значение по умолчанию столбца (`all`) и
сразу попали бы под боевую раскатку. Допустимые значения те же, что в проверке
`devices.ring` (`test`, `early`, `all`); кольцо серийных аппаратов переводит
владелец вручную (`device_set_ring_tz`), когда придёт их очередь.

Результат в `provisioning_out/` (в `.gitignore`, права файлов 600):

| Файл | Содержимое | Куда |
|---|---|---|
| `batch_<дата>.sql` | `insert` в `devices` (id, org_id, токен, name = id, ring) и `device_claims` (соль и хэш кода) | владелец выполняет в SQL Editor |
| `batch_<дата>_labels.csv` | номер аппарата и ОТКРЫТЫЙ код XXXX-XXXX-XXXX | печать наклеек |
| `batch_<дата>_device_config.json` | URL облака, публичный ключ, токен, номер аппарата | запись в аппарат (см. ниже) |
| `issued_ids.txt` | только выданные номера (секретов нет) | защита от повтора |

Если в таблице `devices` есть обязательные столбцы кроме id, org_id, token, name,
добавьте их в `render_sql`.

Повторный запуск с теми же номерами отказывает с понятным сообщением; файлы
одного дня не перезаписываются.

## Хранение (важно)

Файлы `.sql`, `_labels.csv`, `_device_config.json` содержат токены и открытые
коды. Хранить ОФФЛАЙН (зашифрованный носитель), не в git, не в чатах и почте;
после загрузки в базу и записи в аппараты и печати наклеек файлы удалить или
убрать в архив. Токены и коды в отчёты и журналы не попадают (скрипт печатает
только число аппаратов и имена файлов).

## Перевыпуск

* **Код привязки** (потеря наклейки, перепродажа): в панели/SQL от имени
  изготовителя `select claim_regenerate('<номер>');` (только если аппарат не
  привязан; при перепродаже сначала `select access_end('<номер>');`). Новый код
  показывается один раз; старый недействителен.
* **Токен**: сгенерировать новый (`python3 -c "import sys; sys.path.insert(0,'tool');
  import provision_devices as p; print(p.new_token())"`), выполнить
  `update devices set token = '<новый>' where id = '<номер>';` и записать токен в
  аппарат (см. ниже). До записи аппарат получает отказ `auth` на всех запросах —
  работает автономно, но не синхронизируется. Новый токен не печатать и не
  пересылать в чат.
* Номер, уже выданный генератором, перегенерировать заново нельзя (защита от
  молчаливой перезаписи); для осознанного перевыпуска удалите номер из
  `issued_ids.txt` вручную.

## Как данные попадают в аппарат (варианты, выбор за владельцем)

Приложение в R4 не менялось. Сейчас URL облака, ключ и токен вводятся в сервисном
меню вручную (вкладка «Облако») и хранятся в `SharedPreferences` приложения.

1. **Файл конфигурации при прошивке (рекомендуется).** При подготовке аппарата
   `adb push` кладёт `device_config.json` в приватный каталог приложения (или во
   временную папку, откуда приложение при старте один раз читает, применяет и
   удаляет файл). Плюсы: сборка одна для всех, токен вне APK, обновление
   приложения токен не затрагивает (данные приложения сохраняются при
   `pm install -r`). Минусы: нужна доработка приложения (чтение и удаление файла) и
   рабочая станция с `adb`/root на заводе. Риски: файл с токеном лежит на
   станции — права 600, оффлайн, удалять после записи.
2. **Значения по умолчанию в сборке на партию.** URL/ключ/токен зашиваются в APK.
   Плюсы: ничего не вводить. Минусы: токен внутри APK (любой, кто достанет APK,
   получит токен), сборка на КАЖДЫЙ аппарат (подпись и размер — по 20 МБ), раскатка
   обновлений ломается: общий APK для всех нельзя. **Не рекомендуется.**
3. **Ввод в сервисном меню.** Как сейчас. Плюсы: ничего не менять. Минусы: ручной
   ввод 43-символьного токена, ошибки, человеческий фактор, токен виден в экране
   и на фото. Годится для единиц, не для серии.

Обновление приложения (`update_app`/раскатка) данные приложения и токен не
стирает при любом из вариантов 1 и 3.

### Код привязки в сервисном меню

Нужен ли вообще? Если есть наклейка — нет. Но при потере наклейки аппарат без
привязки можно получить новый код через `claim_regenerate`, а в меню показывать
код нельзя (его знает только наклейка: в аппарате и в базе открытого кода нет).
Рекомендация: в меню код не показывать.

### Если токен перевыпущен

`device_poll` вернёт `{"ok":false,"error":"auth"}`; аппарат продолжает работать
автономно (облако не обязательно для продажи), события копятся в очереди (до 500).
После записи нового токена очередь уходит. Автоматического получения нового
токена нет (и не должно быть: это обход защиты).

# Заводской генератор партии аппаратов и запись облачных данных

Скрипт `tool/provision_devices.py` работает локально, без обращения к облаку и без
ключей Supabase (публичный ключ — только как значение для записи в аппарат).

## Как пользоваться

```
export PROVISION_ANON_KEY='<публичный ключ sb_publishable_…>'
tool/provision_devices.py --org-id <uuid организации-изготовителя> \
    --prefix CARFOG- --start 100 --count 20 --cloud-url https://<проект>.supabase.co
# или список:  --list ids.txt   (по одному номеру в строке, # — комментарий)
# кольцо раскатки (по умолчанию test):  --ring test | early | all
# спецификация (одинакова для всей партии): --pumps 4..10  --langs et,en,ru  --default-lang et
# вторая партия в тот же день:  --batch <имя>   (по умолчанию batch_<дата>)
```

**Кольцо.** Генератор записывает `devices.ring` явно в каждом `insert` (по умолчанию
`test`). Иначе новые аппараты получили бы значение по умолчанию столбца (`all`) и
сразу попали бы под боевую раскатку. Допустимые значения те же, что в проверке
`devices.ring` (`test`, `early`, `all`); кольцо серийных аппаратов переводит
владелец вручную (`device_set_ring_tz`), когда придёт их очередь.

Результат в `provisioning_out/<партия>/` (в `.gitignore`, файлы 600, каталоги 700):

| Файл | Содержимое | Куда |
|---|---|---|
| `batch.sql` | `insert` в `devices` (id, org_id, токен, name = id, ring, **spec_pumps, spec_langs, spec_default_lang, hardware_profile**) и `device_claims` (соль и хэш кода) | владелец выполняет в SQL Editor |
| `labels.csv` | номер аппарата, ОТКРЫТЫЙ код XXXX-XXXX-XXXX и «подпись» (например `4 насоса · ET/EN/RU`, только текст для печати) | печать наклеек |
| `configs/<ID>.json` | по ОДНОМУ файлу на аппарат: адрес облака, публичный ключ, токен, номер, `config_id`, `spec` | заводская запись (ниже) |
| `devices.txt` | список номеров партии (без секретов) | сверка |
| `../issued_ids.txt` | только выданные номера (секретов нет) | защита от повтора |

Если в таблице `devices` есть обязательные столбцы кроме id, org_id, token, name,
добавьте их в `render_sql`.

Повторный запуск с теми же номерами отказывает с понятным сообщением; каталог
партии не перезаписывается.

## Хранение (важно)

Файлы `batch.sql`, `labels.csv` и `configs/*.json` содержат токены и открытые
коды. Хранить ОФФЛАЙН (зашифрованный носитель), не в git, не в чатах и почте;
после загрузки в базу, записи в аппараты и печати наклеек файлы убрать в архив
или удалить. Токены и коды в отчёты и журналы не попадают (скрипты печатают
только числа, номера и имена файлов).

## Как облачные данные попадают в аппарат (выбранный способ)

Аппарат после сборки проходит пуско-наладку в цеху (часы, перезагрузки, сбросы
настроек, переустановки приложения). Облачные данные (адрес, публичный ключ,
токен, номер) не должны теряться на этом этапе. Поэтому файл конфигурации
**остаётся на планшете всю наладку**, а приложение само сверяет его с запомненным
при каждом старте и при возврате на передний план.

### Файл

`/sdcard/CarFog/device_config.json` (то же, что `/storage/emulated/0/CarFog/…`).
Формат (JSON, UTF-8):

```
{"format":1,"config_id":"2026-10-08-ab12cd34","device_id":"CARFOG-123",
 "cloud_url":"https://<проект>.supabase.co","anon_key":"sb_publishable_…","token":"…"}
```

`config_id` — идентификатор файла (`<дата>-<8 hex>`); при смене токена генератор
выдаёт новый.

### Спецификация аппарата (`spec`)

Аппараты различаются числом насосов/ароматов и набором языков (задаёт заказчик
при сборке); номер остаётся «глухим» (`CARFOG-100`). Спецификация хранится в базе
(`devices.spec_*`, миграция `20261008000000_r5_spec.sql`) и записывается в файл
конфигурации ключом `spec` (формат файла остаётся 1; старые файлы без `spec`
работают как раньше):

```
"spec":{"pumps":8,"langs":["ru","en","de"],"default_lang":"en","hardware_profile":"sy156-a510"}
```

Контракт: `pumps` — целое 4…10 (по умолчанию 4); `langs` — коды в нижнем регистре,
без повторов, 1…24 шт., порядок = порядок на экране выбора (по умолчанию
`et,en,ru`); `default_lang` — один из `langs` (по умолчанию первый);
допустимые коды: bg cs da de el en es et fi fr ga hr hu it lt lv mt nl pl pt ro ru
sk sl sv uk no. Сейчас переведены только et, en, ru; остальные коды приложение
хранит, но пока не показывает. Заводской файл меняет **только** spec: названия
ароматов, цена, длительность, PIN, флаги оборудования и порт шины не
перезаписываются (названия вносит техник заказчика на месте). Изменить
спецификацию уже выданного аппарата в базе можно функцией
`select device_set_spec('<номер>', <насосов>, array['ru','en'], 'ru');` (только
изготовитель, запись в `staff_audit`); в аппарат она попадает при следующей
заводской записи (новый файл с другим `config_id`).

**Почему именно общий каталог, а не каталог приложения.** Закрытый каталог
приложения (`/data/data/<пакет>`) и app-specific каталог внешней памяти
(`/sdcard/Android/data/<пакет>`) стираются при `pm clear` и переустановке. Файл в
общем каталоге, созданный `adb push`, принадлежит не приложению и **переживает**
и `pm clear`, и удаление/переустановку.

**Как приложение читает и удаляет файл (Android 13).** Нужно разрешение «доступ
ко всем файлам» (`MANAGE_EXTERNAL_STORAGE`, в манифесте уже объявлено). На заводе
оно выдаётся командой (её делает `tool/provision_push.sh`):

```
adb shell appops set ee.carfog.dryfog MANAGE_EXTERNAL_STORAGE allow
```

Выдача сбрасывается при удалении приложения: после `adb uninstall` + установки
выдайте разрешение снова (повторный запуск `provision_push.sh` делает это). Если
разрешения нет или файл недоступен, приложение повторяет чтение и удаление через
root (`su`), как остальные привилегированные операции. **Проверка на реальном
планшете остаётся за владельцем** (см. ниже).

### Правило применения

При каждом старте (и при возврате на передний план) приложение, если файл есть и
корректен (`format` = 1, все поля непустые, `cloud_url` — https, номер из букв, цифр,
`. _ -`): сравнивает `config_id` с последним применённым. Применяет файл, если
`config_id` другой **или** облачные настройки пусты. Записываются только номер,
адрес, ключ, токен и включение облака; остальное (цена, PIN, ароматы, киоск…) не
трогается. Файла нет — ничего не происходит. Битый файл — предупреждение в журнал
**без значений** и работа продолжается.

Последний применённый `config_id` хранится отдельно от настроек, поэтому заводской
сброс (удалённый `factory_reset` сохраняет облачные настройки) его не стирает.
Локальной кнопки «сброс к заводским» в меню нет.

### Последовательность на заводе

1. Генератор: `tool/provision_devices.py …` (один раз на партию); `batch.sql` —
   владельцу в SQL Editor.
2. Станция, по одному аппарату (USB, `adb`):
   `tool/provision_push.sh CARFOG-123 [серийник]` — пишет файл, выдаёт доступ,
   перезапускает приложение, сверяет размер и sha256 («ок» или причина).
3. Пуско-наладка. Любое стирание (сброс настроек, `pm clear`, переустановка) само
   лечится при следующем старте: файл найден и применён снова.
4. В конце наладки: сервисное меню → вкладка «Облако» → **«Завершить
   пуско-наладку»** (с подтверждением): файл удаляется. Если кнопка недоступна:
   `tool/provision_finish.sh CARFOG-123 [серийник]`.
5. Наклейка с кодом привязки — на корпус. Файлы партии — оффлайн.

### Что переживает каждый вид стирания

| Действие | Облачные данные в приложении | Файл | Что дальше |
|---|---|---|---|
| Заводской сброс (удалённый `factory_reset`) | остаются | остаётся | — |
| Стирание данных (`pm clear`) | стираются | **остаётся** | применится при следующем старте |
| Переустановка (`uninstall` + install, `install -r`) | `-r` — остаются; `uninstall` — стираются | **остаётся** | после установки выдать доступ (`provision_push.sh`), применится при старте |
| Сброс Android до заводских | стираются | **стирается** | записать файл заново (`provision_push.sh`) |
| После «Завершить пуско-наладку» | остаются | **удалён** | дальше стирание приложения облако уже не восстановит |

### Риски

* Пока файл лежит в общей памяти, **токен читается по USB/MTP** любым, у кого есть
  физический доступ к аппарату. Поэтому файл удаляется в конце наладки.
* Токен можно перевыпустить: `update devices set token = '<новый>' where id =
  '<номер>';` и записать новый файл с НОВЫМ `config_id` (генератор выдаёт его
  сам). Приложение подхватит его при следующем старте.
* Токен и ключ не попадают в журнал и события (журнал маскирует значения;
  приложение значения вообще не пишет).
* Отозвать доступ можно только пока файл на аппарате: после «Завершить
  пуско-наладку» новый токен вводится вручную (сервисное меню) или записью нового
  файла по adb.

### Что НЕ проверено (остаётся за владельцем)

* Чтение и удаление файла приложением на реальном планшете (RK3568, Android 13,
  userdebug): прямой доступ с `MANAGE_EXTERNAL_STORAGE` и запасной путь через root.
* Что файл действительно переживает `pm clear` и переустановку на этом
  образе системы, и поведение после `adb uninstall` (в частности, видит ли новое
  приложение файл, созданный через adb).
* Серийный планшет Syoung SY156-A510 (другое ядро/SELinux/su).

## Перевыпуск

* **Код привязки** (потеря наклейки, перепродажа): в панели/SQL от имени
  изготовителя `select claim_regenerate('<номер>');` (только если аппарат не
  привязан; при перепродаже сначала `select access_end('<номер>');`). Новый код
  показывается один раз; старый недействителен.
* **Токен**: сгенерировать новый (`python3 -c "import sys; sys.path.insert(0,'tool');
  import provision_devices as p; print(p.new_token())"`), выполнить
  `update devices set token = '<новый>' where id = '<номер>';` и записать новый
  файл (`config_id` другой) через `provision_push.sh` либо ввести токен в
  сервисном меню. До этого аппарат получает отказ `auth` на всех запросах —
  работает автономно, но не синхронизируется. Новый токен не печатать и не
  пересылать в чат.
* Номер, уже выданный генератором, перегенерировать заново нельзя (защита от
  молчаливой перезаписи); для осознанного перевыпуска удалите номер из
  `issued_ids.txt` вручную.

### Код привязки в сервисном меню

Нужен ли вообще? Если есть наклейка — нет. При потере наклейки аппарат без
привязки получает новый код через `claim_regenerate`, а в меню показывать код
нельзя (его знает только наклейка: в аппарате и в базе открытого кода нет).
Рекомендация: в меню код не показывать.

### Если токен перевыпущен

`device_poll` вернёт `{"ok":false,"error":"auth"}`; аппарат продолжает работать
автономно (облако не обязательно для продажи), события копятся в очереди (до 500).
После записи нового токена очередь уходит. Автоматического получения нового
токена нет (и не должно быть: это обход защиты).

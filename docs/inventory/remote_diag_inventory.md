# Опись для удалённой диагностики, этап 1

Дата: 2026-11-03. Смотрел ветку `ixp101m1-profile` (`ea5f87e`), код не менял.
ТЗ: `TZ_Remote_Diagnostics_v1.md` (версия 0 от 2026-11-03).

## Вывод

* Пакет диагностики уже есть и работает: команда `collect_diagnostics` или
  кнопка в сервисном меню, один JSON частями по 128 КБ через `device_diag_put`.
* Секреты вырезаются в два слоя: при записи журнала и перед отправкой
  пакета. Шаблоны: pin/token/key/password/secret/authorization, JWT, Bearer,
  точные значения PIN, токена и ключа. **Шаблона номера карты нет.**
* Журнал приложения свой: 2 файла по 1 МБ, у каждой строки время. Отдать
  «последние N минут» можно, это фильтр по времени.
* В пакет попадают 100 событий и 300 строк журнала, общего потолка размера
  нет. Время сбора — местное без смещения (та же ошибка, что была у событий
  до 1.11.2).
* Не хватает до ТЗ: состояния киоска и сторожа панелей, последних годных
  показаний с временем, статуса терминала, пояса, температуры планшета,
  окна журнала в минутах, потолка 200 КБ, ловушки для номера карты.
* Супервайзер сейчас пакет **прочитать не может**: читать умеет только
  владелец через SQL Editor. Функций чтения и раздела в портале нет.
  `collect_diagnostics` в портале не отправляется (в портале только `ping`,
  `restart_app`, `reset_session`, `update_config`).
* Снимок экрана делается без системных прав: снимок корня Flutter
  (`RepaintBoundary.toImage`) в уменьшенном размере, JPEG сжимается нативно.
  Экран PIN и вкладки с кодами — отказ.
* Оценка: 9–10 рабочих дней (приложение 4–5, база 1,5, портал 3, живая
  проверка 0,5).

## 1. Что собирает `collect_diagnostics` сейчас

Код: `lib/services/diagnostics_service.dart` (сбор и отправка),
`lib/services/remote_commands.dart:211` (команда), лимиты —
`lib/models/remote_limits.dart` (`DiagnosticsLimits`, `CommandLimits`).

| Раздел JSON | Поля |
|---|---|
| `bundle_version`, `collected_at`, `device_id`, `trigger` | версия формата, время (**местное без смещения**), аппарат, кто запустил (`command`/`manual`) |
| `app` | версия, причина запуска, журнал готов |
| `device` (нативный `getDeviceInfo`) | Android, SDK, модель, производитель, fingerprint прошивки, тип сборки, аптайм, диск, память, тип сети, сигнал, RSSI Wi-Fi |
| `state` | экран приложения, код ошибки, вывод из обслуживания (код, с какого времени, подробности), каких устройств не хватает, блок оплаты, шина здорова, кто держит порт (`bus_busy_port`, `bus_busy_pid`) |
| `config` | белый список: `reportedSnapshot()` (цены, профиль, порт, spec…) плюс терминал, «установлено», тариф. PIN, токена и ключа нет |
| `debug_modes`, `reads` | отладочные режимы. Живые чтения термопары, счётчика и выходов — **только в покое**, иначе `skipped: busy_state`. Уровни из кэша |
| `watchdog`, `bus_watchdog`, `detectors`, `trial` | сторож выходов, сторож шины (перезапуски), последняя авария нагрева и пороги, пробный цикл |
| `network` | тип, проверена ли сеть, сигнал, очередь событий, последняя успешная отправка, облако включено |
| `events_tail` | **100** последних событий |
| `log_tail` | **300** последних строк журнала |

**Отправка и хранение:**
* Пакет режется на части по 128 КБ (`DiagnosticsLimits.chunkChars`) и
  уходит через `device_diag_put` с токеном аппарата.
* Нет связи — пакет сохраняется на диск (`diag_pending.json`) и уходит позже
  (`retryPending`). Отказ сервера `quota` или `auth` — пауза 1 час.
* Сервер (`supabase/migrations/20261003000100_r1_diagnostics.sql`): таблица
  `device_diagnostics`, RLS включён, права у anon и authenticated отозваны.
  Квота 600 частей на аппарат.
* Срок хранения 14 дней (`device_diag_purge`). Чистка запускается при
  приёме первой части нового пакета; расписание pg_cron дано только
  комментарием.
* Лимит команды в приложении: не чаще раза в минуту и не больше 3 раз в
  час (`CommandLimits.minInterval`, `maxPerHour`).

**Размер:** не измерен. Если строки журнала около 150 байт, 300 строк
дают ~45 КБ, 100 событий ~20–40 КБ, остальное ~10 КБ. Итого порядка 80–100
КБ, обычно одна-две части. Измерить на CARFOG-001 на этапе 5.

**Очистка (redact):**
* `AppLog.redact` (`lib/services/app_log_service.dart:130`): шаблон
  ключ=значение для `pin`, `service_pin`, `token`, `cloud_token`, `p_token`,
  `anon_key`, `apikey`, `authorization`, `password`, `secret`; JWT
  (`eyJ…`); `Bearer …`; точные значения из `AppLog.setSecrets` (PIN,
  токен, ключ облака, `lib/main.dart`).
* Журнал чистится при записи каждой строки, пакет — по всем строковым
  значениям перед кодированием (`AppLog.redactTree`).
* **Пробелы:** нет шаблона номера карты; в `setSecrets` нет мастер-кода и
  кодов привязки (проверить, попадают ли они в журнал вообще);
  `CardTerminalService.recent` (сырые кадры терминала) в пакет сейчас не
  входит и входить не должен.

Существующие тесты: `test/remote_r1_test.dart` — «секретов нет: ни PIN, ни
токена, ни ключа», «секреты вырезаются: по шаблонам и по точным значениям»,
ответы сервера не оставляют токен в журнале.

## 2. Внутренний журнал приложения

* `AppLog` (`lib/services/app_log_service.dart`): файлы
  `filesDir/app_log.txt` и `app_log.1.txt`, по 1 МБ, ротация при
  переполнении. Запись пачкой раз в секунду с fsync.
* Строка: `2026-11-03T21:35:56.695 [тег] текст`, длина ограничена
  `maxLineChars`.
* Время местное без смещения. Для фильтра «последние N минут» этого
  достаточно (сравнение на самом аппарате), но в пакет лучше добавить пояс и
  смещение.
* Сколько минут помещается в 2 МБ — не измерено. Зависит от активности
  опроса шины: при ошибках шины пишется много. Измерить на CARFOG-001.
* `redact`-слой есть (см. выше).
* Предложение: `AppLog.tailSince(Duration)` — строки не старше N минут
  (15 по умолчанию, максимум 60), затем обрезка со старого конца, пока
  пакет не влезет в 200 КБ.

## 4. Снимок экрана

**Как снимать без системных прав:**
1. `RepaintBoundary` вокруг корня приложения (в `MaterialApp.builder`) и
   `toImage(pixelRatio: k)`, где k подобран так, чтобы длинная сторона
   стала 800 px. Сразу маленькая картинка: в памяти около 800×450×4 ≈
   1,5 МБ (альбом IXP) и 800×1422×4 ≈ 4,5 МБ (портрет Syoung).
2. JPEG: во Flutter нет встроенного кодировщика. Предлагаю отдавать байты
   RGBA в Kotlin и делать `Bitmap.compress(JPEG, 70)` (быстро, без новых
   библиотек). Ожидаемый вес 60–120 КБ, после base64 80–160 КБ.
3. Запасной вариант — нативный `PixelCopy` окна приложения: снимает и видео,
   и всё окно, но тоже без системных панелей.

**Видео заставки (SD-карта)** играет через `video_player`, то есть через
текстуру Flutter (`Texture`). `toImage` обычно включает текстуры, но на
части Android-устройств кадр видео выходит чёрным. Проверить на
CARFOG-001. Если чёрный — для заставки с видео использовать `PixelCopy`.

**Где снимок запрещён** (проверка до съёмки, ответ
`{"refused":"pin_screen"}`):
* `AppState.servicePinEntry` — экран PIN, включая мастер-код и смену PIN;
* сервисное меню целиком (`AppState.serviceMenu`): там есть поля PIN,
  кодов, настроек облака. Проще и надёжнее запретить меню всё, чем
  перечислять вкладки. Если владельцу нужны снимки вкладок «Датчики» и
  «Диагностика» — отдельным решением;
* открытый диалог ввода PIN поверх любого экрана (смена порта шины и др.):
  флаг «идёт ввод секрета», который ставят такие диалоги.

**Память на слабых планшетах:** снимок разовый, по команде, не чаще раза
в минуту. В покое приложение занимает немного, 2–5 МБ на снимок
безопасно. Во время цикла (`payment`, `preparing`, `treating`) снимок
можно разрешить — он не трогает шину, — но в первой версии предлагаю
делать только в покое, как живые чтения шины.

## 5. Команды из облака
* Приложение опрашивает `device_poll` раз в 30 с. Ответ:
  `commands[]` (`id`, `action`, `params`, `created_at`), `target`,
  `server_time`.
* `RemoteCommands` (`lib/services/remote_commands.dart`): белый список
  `ping`, `unlock`, `set_pin`, `update_config`, `factory_reset`,
  `reset_session`, `collect_diagnostics`, `restart_app`, `update_app`,
  `rollback_app`. Есть явно запрещённые (снятие вывода из обслуживания).
* Защиты: идемпотентность по `command_id` (помнит 200), срок жизни команды
  10 минут по часам сервера, опасные команды без `created_at` не
  выполняются, лимиты частоты у `collect_diagnostics` и `restart_app`.
* Ответ — `device_ack` с текстом результата.
* `capture_screen` встраивается рядом с `collect_diagnostics`: в белый
  список, свой лимит (раз в минуту, 3 в час), ответ
  `{"shot_id":…, "size_bytes":…}` или `{"refused":"pin_screen"}`.
  Загрузка — новой RPC `device_shot_put` по образцу `device_diag_put`
  (своя таблица, срок 24 часа).
* Тело `supervisor_send_command` в репозиториях отсутствует: неизвестно,
  пропустит ли оно новые действия. Нужен его текст или отдельная функция
  `supervisor_request_diag`.

## 6. Тесты приватности (ловушки)
1. В журнал через `AppLog.log` пишутся строки-ловушки:
   * `token=TRAP_TOKEN_123456`, `"pin":"4729"`, `Authorization: Bearer abc.def.ghi`;
   * JWT-подобная строка;
   * номер карты `4111 1111 1111 1111`, а также слитно и через дефисы;
   * точные значения PIN, токена и ключа из `setSecrets`.
2. Собирается пакет (`DiagnosticsService.collect` + `encode`).
3. Проверка: ни одной ловушки в тексте пакета, вместо них `***`; JSON
   валиден; размер не больше 200 КБ.
4. Отдельно: ловушки в `events_tail` (данные события) и в `config`.
5. Снимок: при `servicePinEntry` и `serviceMenu` ответ `refused`,
   картинка не создаётся (мок канала не вызывается).

Номер карты: шаблон 13–19 цифр (с пробелами или дефисами) с проверкой
Luhn, чтобы не вырезать время и счётчики.

## 7. Объём и риски

| Этап | Работа | Дней |
|---|---|---|
| Приложение | пакет: новые поля, UTC, пояс, 20 событий, журнал по минутам, потолок 200 КБ | 1,5 |
| | очистка: номер карты, мастер-код и коды привязки, ловушки | 0,5 |
| | `capture_screen`: снимок, JPEG в Kotlin, запреты, загрузка, лимиты | 1,5 |
| | тесты, golden Syoung и альбом IXP без изменений | 1 |
| База | `device_screenshots`, `device_shot_put`, очистка 24 ч, функции чтения супервайзера (aal2), `staff_audit`, SQL-тесты прав | 1,5 |
| Портал | карточка: кнопки, статус, светофор, журнал (поиск, .txt), снимок; клиенту только светофор | 3 |
| Живая проверка | CARFOG-001: пакет, снимок заставки с видео, отказ на PIN, размер | 0,5 |
| **Итого** | | **9–10** |

**Риски:**
* Видео может выходить чёрным на снимке: нужен `PixelCopy`.
* Без pg_cron снимки чистятся не ровно через 24 часа, а при приёме
  следующего.
* Квота 600 частей и потолок 200 КБ держат базу, но снимки нужно считать
  отдельно (своя таблица и квота).
* Светофор для клиента строить по `reported_config` и событиям, а не по
  пакету: пакет клиенту не отдаётся вообще.
* `collected_at` и журнал в местном времени без смещения: в пакете
  переводить в UTC, иначе в портале будут сдвиги (как было с +8 ч).

# Шаг 32 — киоск-режим, первый заход (обратимые изменения)

Device Owner и Lock Task сюда не входят — они ставятся один раз через adb
на планшет без учётных записей Google, снимаются только полным сбросом, и
делаются на финальной сборке перед сдачей аппарата. Всё описанное ниже
можно включать/выключать без сброса планшета.

**Все задачи (0-6) проверены вживую на планшете и работают полностью**,
включая автозапуск после `adb reboot` и автоматический перезапуск после
`am crash` — без единого касания экрана. Ключевой момент, из-за которого
это едва не осталось нерабочим без Device Owner: приложение в роли
домашнего экрана запускается не через обычный путь "старт активности из
фона" (который Android блокирует), а через отдельный привилегированный
путь, которым система гарантирует существование рабочего стола. Подробности
и требуемая настройка — в разделах про задачи 1-4 ниже.

## Задача 0 — Modbus-шина и главный поток

Канал `com.carfog.dryfog/modbus` уже с Шага 30 (коммит `35b4e7c`) выполняется
на фоновой `BinaryMessenger.makeBackgroundTaskQueue()`, а не на UI-потоке —
это уже снимает риск ANR. Оставшееся реальное подвисание диагностики было
вызвано не потоком, а тем, что `_readEnergy()` в `service_menu.dart` дёргала
и `readEnergy()`, и `getMonthlyEnergy()` подряд каждые 3 секунды, а
`getMonthlyEnergy()` внутри себя ещё раз гонял те же 4 Modbus-транзакции —
итого 8 блокирующих запросов на цикл вместо 4. Исправлено кэшем в
`ModbusChannel.readEnergyValues()`: значение, прочитанное недавно (не
позже 2 секунд назад), переиспользуется вместо повторного опроса шины.

## Задача 2/3 — киоск-режим (роль домашнего экрана) — обязательно для 1 и 4

`KioskHomeAlias` — activity-alias с фильтром `HOME`/`DEFAULT`, выключен по
умолчанию в манифесте. Тумблер "Киоск-режим" в сервисном меню (вкладка
"Киоск") включает/выключает его через `PackageManager` во время работы —
менять манифест для этого не нужно.

**Правильная настройка при первом включении (проверено вживую, оба шага
обязательны):**
1. При включении тумблера открывается системный экран "Приложение по
   умолчанию → Домашний экран" — выбрать там это приложение.
2. Затем один раз нажать "Домой" на планшете. Если снова появится диалог
   выбора ("Только сейчас/Всегда") — обязательно выбрать это приложение и
   нажать **"Всегда"**, не "Только сейчас".

Оба шага нужны по разным причинам, подтверждённым экспериментально: шаг 1
(экран настроек, `RoleManager`) достаточен, чтобы кнопка "Домой" сразу
открывала приложение, но **не** достаточен для автоматического
восстановления после сбоя без касаний — самостоятельный перезапуск
домашнего приложения системой (задача 4) опирается на отдельный, более
старый механизм Android — "предпочитаемая activity" для намерения HOME,
который заполняется именно диалогом "Всегда" из шага 2, а не выбором на
экране настроек. Без шага 2 первый же `am crash` в тестах не восстанавливал
экран сам — только после явного "Всегда" в диалоге второй и все следующие
сбои восстанавливались автоматически.

**После каждого обновления APK эту настройку придётся повторить.** Android
сбрасывает вручную выставленный статус компонента `KioskHomeAlias` обратно
к значению из манифеста при замене пакета (подтверждено логом
`RoleControllerService: Removing package that no longer qualifies for the
role... HOME`). `PackageUpdateReceiver` перевключает сам компонент сразу
после обновления (слушает `MY_PACKAGE_REPLACED`), но саму роль — назначение
"кто именно домашний экран" — по своей инициативе, без участия человека,
переназначить нельзя: это намеренное ограничение Android (RoleManager не
даёт приложению самому себе назначить роль без подтверждения пользователем).
Поэтому после каждого обновления нужно так же один раз пройти оба шага
настройки выше.

Кнопка "Открыть системный рабочий стол" на вкладке "Киоск" открывает тот же
экран настроек в любой момент — без неё выйти из включённого киоска для
обслуживания планшета было бы нечем.

## Задача 1 — автозапуск после подачи питания

`BootReceiver` слушает `BOOT_COMPLETED` и `LOCKED_BOOT_COMPLETED`. Пока
киоск-режим настроен (см. выше), в собственном запуске приложения из этого
приёмника нет нужды: система сама поднимает домашнее приложение при
загрузке — привилегированным путём (`from uid 0` в логе
`ActivityTaskManager`), который не подпадает под ограничение на старт
активности из фона. Проверено вживую (`adb reboot`): приложение поднимается
само, без единого касания экрана, всегда.

`BootReceiver` при этом не бездействует — он остаётся рабочей подстраховкой
на случай, если киоск-режим почему-то выключен (например на планшете
разработчика): тогда он запускает `MainActivity` обычным путём. Пока же
роль домашнего экрана активна, приёмник сам определяет это через
`PackageManager.getComponentEnabledSetting()` и намеренно ничего не делает
— иначе на каждой загрузке поднимались бы два независимых экземпляра
движка Flutter одновременно (лишняя нагрузка и задвоенные события в
журнале — так и было до этого исправления).

Отдельно, независимо от вышесказанного: на части китайских/вендорских
прошивок (в т.ч. встречается на RK3568-платах) бывает собственный список
автозапуска в системных настройках, независимый от разрешения
`RECEIVE_BOOT_COMPLETED`. На этом конкретном планшете (сборка `rockchip`,
без брендированной оболочки типа MIUI) такого пункта в проверенных разделах
настроек не нашлось — но раз автозапуск и так работает через роль домашнего
экрана, актуально это может стать только если киоск-режим по какой-то
причине выключен.

## Задача 5 — экран не гаснет

`FLAG_KEEP_SCREEN_ON` выставлен в `MainActivity.onCreate()`. Флаг работает,
пока приложение на переднем плане, но перекрывает не все прошивки и
энергосберегающие режимы (некоторые OEM-прошивки экономии энергии могут
гасить экран поверх флага). Дополнительно, при первичной настройке
планшета, в системных настройках экрана таймаут "Спящий режим/Заставка"
нужно выставить в "Никогда".

## Задача 4 — аварийное выключение при сбое

`DryFogApplication` ставит `Thread.setDefaultUncaughtExceptionHandler` при
старте процесса. При необработанном исключении: выключает ТЭН и компрессор
первыми, затем насосы 0-7 и LED, напрямую через `ModbusChannel.activeBus`
(минуя Flutter), с потолком ожидания 2 секунды; записывает признак аварии в
`SharedPreferences` (`commit()`, синхронно); планирует перезапуск через
`AlarmManager` + промежуточный `BroadcastReceiver` (`RestartReceiver`);
завершает процесс.

**Всё проверено вживую, включая полностью автоматический перезапуск.**
Порядок подтверждения того, что происходило:
- Выключение оборудования: включил для теста ТЭН, компрессор и насос 1,
  вызвал настоящий `am crash` — все три канала гарантированно выключились.
- Двухсекундный потолок по времени: при заблокированном ответе шины
  обработчик реально прерывался по таймауту (не висел бесконечно).
- Автоматический перезапуск: **работает, но только когда роль домашнего
  экрана настроена правильно** (оба шага из раздела "Задача 2/3" выше,
  включая "Всегда" в диалоге). Без этого `RestartReceiver` действительно
  утыкается в `ActivityTaskManager: Abort background activity starts` —
  так и было в первых тестах, пока роль не была настроена до конца; после
  правильной настройки `am crash` → экран сам восстанавливается за
  секунды, без единого касания, признак аварии и событие в облаке (задача
  6) корректно записываются каждый раз.

## Задача 6 — причина запуска в облаке

Событие `app_started` — обычный запуск (данные `{reason: 'boot'}` для
запуска после перезагрузки). Аварийный перезапуск — отдельный тип события
`app_started_after_crash`, без вложенных полей: и локальный журнал
сервисного меню, и веб-панель (Supabase, вне этого репозитория) могут
подсвечивать его тревожным цветом простым фильтром по типу события. Веб-
панель нужно поправить отдельно — в этом репозитории только формирование
события на стороне аппарата. Проверено вживую: каждый `am crash` даёт ровно
одну красную запись "Запуск после аварийного завершения" в Журнале, без
дублей и без ложных срабатываний на обычных запусках.

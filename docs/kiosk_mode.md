# Шаг 32 — киоск-режим, первый заход (обратимые изменения)

Device Owner и Lock Task сюда не входят — они ставятся один раз через adb
на планшет без учётных записей Google, снимаются только полным сбросом, и
делаются на финальной сборке перед сдачей аппарата. Всё описанное ниже
можно включать/выключать без сброса планшета.

**Главный вывод по итогам живой проверки на планшете:** на этой прошивке
Android блокирует запуск Activity из фона (`Abort background activity
starts`) даже для `BOOT_COMPLETED` и для собственных `AlarmManager`-триггеров
— это касается и задачи 1 (автозапуск после питания), и автоматической
части задачи 4 (перезапуск после сбоя). Код обеих задач написан правильно
и по официально рекомендуемым паттернам — ограничение снимается только
правами Device Owner, которые в этом шаге сознательно отложены. Все
остальные задачи (0, 2, 3, 5, 6) проверены вживую и работают полностью.
Подробности — в разделах ниже.

## Задача 0 — Modbus-шина и главный поток

Канал `com.carfog.dryfog/modbus` уже с Шага 30 (коммит `35b4e7c`) выполняется
на фоновой `BinaryMessenger.makeBackgroundTaskQueue()`, а не на UI-потоке —
это уже снимает риск ANR. Оставшееся реальное подвисание диагностики было
вызвано не потоком, а тем, что `_readEnergy()` в `service_menu.dart` дёргала
и `readEnergy()`, и `getMonthlyEnergy()` подряд каждые 3 секунды, а
`getMonthlyEnergy()` внутри себя ещё раз гонял те же 4 Modbus-транзакции —
итого 8 блокирующих запросов на цикл вместо 4. Исправлено кэшем в
`ModbusChannel.readEnergyValues()`: значение, прочитанное недавно (не
позже 2 секунд назад), переиспользуется вместо повторного опроса шины.

## Задача 1 — автозапуск после подачи питания

`BootReceiver` слушает `BOOT_COMPLETED` и `LOCKED_BOOT_COMPLETED` и
запускает `MainActivity` новой задачей.

**⚠️ Не работает на этом планшете без Device Owner.** Проверено вживую
(`adb reboot`): приёмник срабатывает, `Intent` до `MainActivity` доходит,
но система блокирует сам запуск активности с явной ошибкой в логе —
`ActivityTaskManager: Abort background activity starts from <uid>`. Это
ограничение Android на старт активности из фона (background activity
start), которое на этой прошивке распространяется даже на широковещательные
приёмники системных событий вроде `BOOT_COMPLETED` — не только на
приложения собственной разработки (на стоковом AOSP `BOOT_COMPLETED` обычно
в списке исключений, здесь — нет). Это не ошибка кода: тот же самый Intent
успешно запускает приложение при вызове с правами adb shell или обычным
касанием иконки — блокируется именно запуск "из фона". Полноценно это
снимается только правами Device Owner (шаг явно отложен на финал). Пока он
не поставлен, автозапуск после перезагрузки/пропадания питания придётся
либо не полагаться на него, либо проверить вендорский список автозапуска
(см. ниже) — не факт, что поможет, но это единственный доступный без
Device Owner рычаг.

Отдельно (независимо от блокировки выше): на части китайских/вендорских
прошивок (в т.ч. встречается на RK3568-платах) есть собственный список
автозапуска в системных настройках (обычно "Настройки → Приложения →
Автозапуск" или аналог в разделе безопасности/энергосбережения),
независимый от разрешения `RECEIVE_BOOT_COMPLETED`. На этом конкретном
планшете (сборка `rockchip`, без брендированной оболочки типа MIUI) такого
пункта в проверенных разделах настроек не нашлось, но стоит проверить
отдельно при следующей ревизии прошивки.

## Задача 5 — экран не гаснет

`FLAG_KEEP_SCREEN_ON` выставлен в `MainActivity.onCreate()`. Флаг работает,
пока приложение на переднем плане, но перекрывает не все прошивки и
энергосберегающие режимы (некоторые OEM-прошивки экономии энергии могут
гасить экран поверх флага). Дополнительно, при первичной настройке
планшета, в системных настройках экрана таймаут "Спящий режим/Заставка"
нужно выставить в "Никогда".

## Задача 2/3 — киоск-режим (роль домашнего экрана)

`KioskHomeAlias` — activity-alias с фильтром `HOME`/`DEFAULT`, выключен по
умолчанию в манифесте. Тумблер "Киоск-режим" в сервисном меню (вкладка
"Киоск") включает/выключает его через `PackageManager` во время работы —
менять манифест для этого не нужно. При включении сразу открывается
системный экран "Приложение по умолчанию → Домашний экран"
(`Settings.ACTION_HOME_SETTINGS`) — на нём нужно выбрать это приложение.
Кнопка "Открыть системный рабочий стол" на той же вкладке открывает тот же
экран в любой момент — без неё выйти из включённого киоска для
обслуживания планшета было бы нечем.

## Задача 4 — аварийное выключение при сбое

`DryFogApplication` ставит `Thread.setDefaultUncaughtExceptionHandler` при
старте процесса. При необработанном исключении: выключает ТЭН и компрессор
первыми, затем насосы 0-7 и LED, напрямую через `ModbusChannel.activeBus`
(минуя Flutter), с потолком ожидания 2 секунды; записывает признак аварии в
`SharedPreferences` (`commit()`, синхронно) — **эта часть проверена вживую
и работает надёжно**: у трёх включённых для теста каналов (ТЭН, компрессор,
насос 1) `am crash` гарантированно приводил к их выключению.

**⚠️ Автоматический перезапуск после сброса — не работает на этом
планшете без Device Owner**, той же природы, что и у задачи 1. Проверены
вживую три разных механизма — все заблокированы одинаковой ошибкой
`Abort background activity starts`:
1. `AlarmManager.setAndAllowWhileIdle()` + `PendingIntent.getActivity()` напрямую.
2. То же через промежуточный `BroadcastReceiver` (`RestartReceiver`).
3. `AlarmManager.setAlarmClock()` (требует `SCHEDULE_EXACT_ALARM`, добавлено
   и подтверждено выданным) + тот же `BroadcastReceiver`.

Код (вариант 3, `RestartReceiver` + `setAlarmClock`) оставлен в проекте —
это официально рекомендуемый Android-паттерн и корректная реализация, она
просто упирается в ограничение фона именно на этой прошивке. Признак
аварии в `SharedPreferences` и событие в облаке (задача 6) при этом
записываются корректно независимо от того, поднимется ли UI сам — если
кто-то откроет приложение вручную после сбоя (или это произойдёт после
следующей перезагрузки), причина "после аварии" не потеряется.

Значит: ограничить время выключения удалось (двухсекундный
`CountDownLatch` подтверждён вживую — при заблокированном ответе шины
обработчик реально прерывался по таймауту, а не висел), но "приложение
перезапустилось само" из критерия приёмки задачи 4 требует Device Owner.

## Задача 6 — причина запуска в облаке

Событие `app_started` — обычный запуск (данные `{reason: 'boot'}` для
запуска после перезагрузки). Аварийный перезапуск — отдельный тип события
`app_started_after_crash`, без вложенных полей: и локальный журнал
сервисного меню, и веб-панель (Supabase, вне этого репозитория) могут
подсвечивать его тревожным цветом простым фильтром по типу события. Веб-
панель нужно поправить отдельно — в этом репозитории только формирование
события на стороне аппарата.

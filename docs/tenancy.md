# Модель «изготовитель — клиент» (R4)

Миграция: `supabase/migrations/20261007000000_r4_tenancy.sql` (выполняет только
владелец, SQL Editor), после неё отдельной командой `notify pgrst, 'reload schema';`.
Проверка прав: `supabase/tests/rls_tenancy.sql` (копия базы, три пользователя,
в конце rollback).

## Роли

* **Изготовитель («супервизор»)** — член организации (`org_members`), которой
  принадлежит аппарат (`devices.org_id`). Навсегда видит ВСЕ аппараты: логи,
  обновления, раскатки, диагностику. Аппарат всегда принадлежит изготовителю;
  клиент в `org_id` не переносится.
* **Клиент** — одна учётная запись `auth.users`, НЕ член организации. Видит и
  делает только то, что дают представления `customer_*` и функции клиента.
  Сотрудников и ролей внутри клиента нет. Дистрибьюторов нет.
* **Связь** `device_access`: аппарат ↔ клиент со сроком подписки
  (`valid_until`) для КАЖДОГО аппарата отдельно. «Активный доступ» =
  `ended_at is null и valid_until > now()`. Не более одной открытой связи на
  аппарат.

## Кто что видит и может

| | Изготовитель | Клиент (активный доступ) | Клиент (просрочка / нет связи) |
|---|---|---|---|
| Базовые таблицы (devices, events, commands, diagnostics, rollouts…) | да | **нет никогда** | нет |
| `customer_devices` | — | свои аппараты: имя, на связи/нет, срок, цена, длительность, число и названия ароматов, «выведен из обслуживания», пустые канистры | пусто |
| `customer_events` | — | события из списка `customer_event_types`, только разрешённые ключи `data`, только с момента привязки | пусто |
| `customer_commands` | — | свои команды, статус, короткий результат | пусто |
| Команды | любые (панель, `insert into commands`) | только через `customer_send_command`: `ping`, `restart_app`, `reset_session`, `update_config` (цена 50…2000 центов, длительность 10…120 с); не более 20 в час на аппарат | отказ |
| Переименовать аппарат | — | `device_set_label` | отказ |
| Срок подписки, закрыть связь, новый код | `access_set_valid_until`, `access_end`, `claim_regenerate` | нет | нет |
| Журнал действий (`staff_audit`) | да | нет | нет |

Клиенту НЕ отдаются: токен, версия приложения, rollback, adb, debug_modes,
last_update_result, skip_health_signal_build, rollout_*, ring, timezone, org_id.
Список типов событий и разрешённых ключей — таблица `customer_event_types`
(`duplicate_payment` в приложении сейчас не существует, есть `unexpected_payment`;
оба в списке). Выручку клиент считает по `session_complete` (`price_cents`,
`paid_cents`): отдельных агрегатов нет — так проще.

## Привязка по коду

1. На заводе генератор (`tool/provision_devices.py`, см. `docs/provisioning.md`)
   создаёт для аппарата токен и код привязки XXXX-XXXX-XXXX (12 знаков без
   0/O/1/I/L). В БД попадают только соль и хэш `sha256(соль + код)`; открытый код
   — только на наклейке (файл `_labels.csv`, хранить оффлайн).
2. Клиент входит в панель и вызывает `device_claim(номер, код, имя)`. По одному
   номеру привязать нельзя. Неверный номер, неверный код и «уже привязан» дают
   один ответ `invalid_claim`. Блокировка: 5 неудач в час на пользователя и 50 в
   сутки на аппарат; во время блокировки верный код тоже отказывает. Порог на
   аппарат намеренно высокий: подбор кода невозможен (31^12 ≈ 2^59), а номер
   аппарата угадывается, и низкий порог позволял бы любому зарегистрированному
   пользователю блокировать привязку честному клиенту.
3. Привязка создаёт связь со сроком `valid_until = момент привязки`, то есть
   подписка ещё не оплачена: до продления клиент ничего не видит. Срок задаёт
   `access_set_valid_until` (вручную изготовитель; позже — вебхук Stripe).
4. Имя аппарата клиент задаёт при привязке и может менять (`device_set_label`).

## Что произойдёт

* **Просрочка подписки.** Отключается только доступ клиента к панели (все
  `customer_*` пусты, команды отказывают). Работа аппарата, обновления и
  телеметрия для изготовителя не меняются; данные не удаляются. После продления
  клиент снова видит всё, в том числе события за время просрочки (но не до
  привязки).
* **Перепродажа / возврат.** Изготовитель: `access_end(номер)` → старый клиент
  теряет всё; `claim_regenerate(номер)` выдаёт НОВЫЙ код (показывается один раз,
  старый недействителен; только если аппарат не привязан); новый клиент
  привязывается новым кодом и не видит события предыдущего владельца.
* **Потеря наклейки.** Если аппарат не привязан — `claim_regenerate`. Если
  привязан — клиент уже в панели; другой код не нужен. Привязанный аппарат другому
  не выдать, пока изготовитель не закроет связь.
* **Токен перевыпущен** — см. `docs/provisioning.md`.

## Журнал действий изготовителя

Таблица `staff_audit` (кто, что, когда, аппарат): вставка команд изготовителем
(триггер на `commands`), смена статуса раскатки, `device_set_ring_tz`,
`access_set_valid_until`, `access_end`, `claim_regenerate`. Читает только
изготовитель; клиенту не отдаётся (решение о показе — позже).

## Исправленные дефекты прав (аудит при R4)

* **A.** `commands_insert` не проверял, что `device_id` принадлежит организации
  `org_id`: член организации X мог вставить команду для аппарата организации Y
  (`device_poll` выбирает команды по одному `device_id`). Исправлено политикой и
  триггером `commands_device_org_check`.
* **B.** У `authenticated` на `devices` оставались INSERT, UPDATE, REFERENCES (в
  том числе на `token`), записи не было только из-за отсутствия политик. Права
  отозваны на уровне таблицы (как для `app_releases`, `rollouts`). Аналогично
  закрыты запись и лишние права на `commands` (UPDATE/DELETE), `events`,
  `device_diagnostics`; у `anon` на эти таблицы права отозваны.
* Новый столбец `devices` требует явного `grant select (<столбец>) … to
  authenticated`.

## MFA для изготовителя (не реализовано, как включить)

Все проверки прав изготовителя в функциях R4 идут через `public.is_staff(org)`
(сейчас = `is_org_member`). Чтобы потребовать второй фактор:
1. В Supabase Auth включить MFA (TOTP) и зарегистрировать фактор для учётных
   записей изготовителя.
2. В панели изготовителя после входа выполнить `mfa.challenge` / `mfa.verify`,
   чтобы сессия получила уровень `aal2` (в JWT `aal = aal2`).
3. Изменить одну функцию:
   `select public.is_org_member(p_org) and coalesce(auth.jwt() ->> 'aal','') = 'aal2';`
   — и те же условия в политиках изготовителя (`devices`, `events`, `commands`,
   `commands_insert`), которые сейчас вызывают `is_org_member` напрямую.
4. Проверить `rls_tenancy.sql` под сессией aal2 и под aal1 (последняя должна
   получать отказ).

## Перед запуском клиентской панели (действия владельца, в SQL их нет)

1. В Supabase Auth включить **подтверждение email** при регистрации (иначе чужой
   адрес даёт неподтверждённый вход).
2. Пароль не короче **10 знаков** (Auth → Providers → Email → minimum password
   length).
3. Защита от ботов (**CAPTCHA**, например hCaptcha или Turnstile) на регистрации и
   входе.
4. Отдельный **свой домен для API** (custom domain) до публичного запуска.

## Stripe (следующий этап)

Вебхук (Edge Function с service role) после оплаты вызывает
`access_set_valid_until(<номер>, <новая дата>, 'stripe', <id подписки>)` (execute
выдан `service_role`), при отмене/возврате — ту же функцию с датой в прошлом.
Клиентская панель, сайт, оплата — вне этого этапа.

## Предложение: хэширование токенов устройств (не сделано)

Сейчас `devices.token` хранится открыто (и `device_poll` сравнивает как есть).
Токен — 32 случайных байта, поэтому медленный хэш не нужен: достаточно
`devices.token_hash = sha256(token)`. План: добавить столбец, заполнить
`encode(sha256(convert_to(token,'UTF8')),'hex')`, перевести проверку (в
`device_token_valid`, `device_poll`, `device_report`, `device_ack`) на сравнение
хэша, одну версию держать двойную проверку, затем удалить открытый токен;
генератор тогда записывает только хэш, а токен остаётся лишь в файле для записи в
аппарат. Риск: потерянный токен нельзя «посмотреть» — только перевыпустить.

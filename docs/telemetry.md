# Шаг 33 — телеметрия

Схема полей ниже фиксирована — веб-панель и SQL-отчёты живут вне этого
репозитория, менять имена полей задним числом дорого. При правке
добавляйте новые поля, не переименовывайте существующие.

## Событие `session_complete`

Отправляется ровно один раз на сессию — либо из `treating.dart` (успех,
после продувки, до перехода на `finished`), либо из `preparing.dart`/
`payment.dart` (прерывание). Идемпотентно: `SessionService` помнит, что
сессия уже завершена/прервана, повторный вызов ничего не шлёт.

Сессия **начинается** в `payment.dart`, в момент, когда внесённой суммы
стало достаточно (до перехода на подготовку) — до этого момента отмена
или таймаут оплаты вообще не создают контекст сессии, событий нет.

```
{
  "flavor_index": 2,
  "flavor": "Хвоя",          // всегда по-русски — событие для оператора
  "price_cents": 200,
  "paid_cents": 300,          // может быть больше price_cents — сдачи нет
  "duration_s": 40,
  "energy_wh": 34.2,          // ОТСУТСТВУЕТ, если хоть одно из двух
                               // показаний счётчика (старт/финиш) не
                               // удалось прочитать — не нуль, а просто
                               // нет поля
  "completed": true
}
```

При `completed: false` добавляется `"reason"`:
- `overheat` — превышен аварийный потолок 240°C (preparing.dart)
- `timeout` — не вышли на 225°C за 10 минут, при этом термопара всё
  это время отвечала нормально (иначе см. `sensor` ниже)
- `sensor` — термопара молчала или устойчиво (≥5 тиков подряд, ~15 сек)
  отдавала код "нет датчика" модуля HLS-KWL-4TC (~-500°C) — раньше это
  тонуло в обычном `timeout` без объяснения причины
- `cancelled` — клиент отменил уже оплаченную сессию кнопкой "Отмена" на
  экране прогрева. Это решение шире буквального текста Шага 33 (там
  прерывание требовалось только для overheat/timeout) — но деньги на
  этом экране уже приняты монетоприёмником безвозвратно, и без этого
  события выручка в облаке разошлась бы с копилкой аппарата.

## Уровень канистр — `low_liquid` / `liquid_restored`

`LevelService` отслеживает переход состояния каждого канала (не текущее
значение) — событие уходит один раз в момент опустошения/заправки, а не
на каждом трёхсекундном опросе. Обрабатываются только каналы
`0..kFlavorCount-1` — остальные физически не распаяны. Самое первое
успешное чтение после запуска приложения считается исходным состоянием
и события не создаёт (иначе на каждом включении аппарата летела бы пачка
ложных сообщений по уже известному состоянию).

```
{"channel": 3, "flavor": "Лаванда"}
```

## `energy_reading` — раз в час

Встроено в `SyncService._tick()` (интервал опроса 30 сек в состоянии
покоя), отдельный таймер не заводился — пауза на время приёма денег и
техпроцесса там уже была (`_isBusyState`), поэтому "не снимать во время
работы" получилось бесплатно, реюзом. Момент последнего успешного снимка
хранится в памяти (`SyncService._lastEnergyReadingAt`); если снимок не
удался (шина всё же занята, ошибка чтения) — время не обновляется, и
попытка просто повторяется на следующем тике, естественным образом
"откладываясь" без отдельной логики ретраев.

```
{"voltage": 231.4, "current": 0.02, "power": 4.0, "total_kwh": 12.34, "month_kwh": 3.21}
```

## `hardware_error`

Три источника:
- `modbus_open_failed` — порт не открылся при старте (`main.dart`),
  поле `port`
- `overheat` — тот же аварийный потолок, что и `session_complete.reason`,
  но отдельным событием с полем `temp_c` (`preparing.dart`)
- `thermocouple_fault` — устойчивый отказ термопары (см. `sensor` выше),
  `temp_c` включается, только если было хоть одно числовое (пусть и
  "код ошибки") показание — при постоянном `null` поля нет вовсе

## Журнал сервисного меню

`session_complete` и `liquid_restored` — обычные (бирюзовые) события,
`low_liquid` — предупреждение (жёлтое), `hardware_error` — тревога
(красное). Лимит локальной истории поднят со 200 до 500 записей — на
200 новые почасовые `energy_reading` (24/сутки) вытесняли бы важные
события за 2-3 дня.

## Попутный фикс, не из этого шага напрямую

`ModbusService.readEnergy()` раньше на ошибке чтения тихо возвращал
нулевую заглушку вместо `null` — в отличие от `readLevels()`/
`readTemperature()`, уже следовавших правилу "null, а не подмена нулём".
Без этого расход за сессию (поле `energy_wh`) в принципе нельзя было бы
корректно пропускать при сбое чтения — разница со скрытым нулём считалась
бы как настоящее число. Приведено к общему паттерну; единственный другой
вызывающий код (вкладка "Диагностика" в сервисном меню) просто оставляет
последнее показание на экране, если новое прочитать не удалось.
